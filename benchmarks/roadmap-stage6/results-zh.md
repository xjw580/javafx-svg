# 阶段 6：兼容性、资源与性能验证记录

## 验证范围

Linux、Java 21、JavaFX 21.0.8、Monocle 软件渲染。Windows/GPU 环境未授权，未验证；不声明浏览器逐像素一致。公开真实语料为四个原字节 Lucide 图标，Git blob 身份、来源与完整许可保存在 `src/test/resources/svg/real-corpus/`。它们覆盖基础路径/描边，不代表复杂 SVG 全覆盖。既有三个用户 SVG 与各阶段自编数值/功能样例保持在全量测试中，二者不混称真实语料。

## 资源复用与安全回归

定位文字的多个字形原先分别申请同一整段布局的径向渐变栅格。现在只在单次 text/tspan 布局构建中，按原 SVG owner、计算样式对象身份、fill/stroke 通道与绘制引用复用。不同 span、透明度动画、视图与替换文档仍隔离，现有回滚列表继续单独负责释放。未提高任何像素预算，未改变采样内核，也不据此宣称计时加速。

六项针对性测试验证：60 个定位字形在 50,000 像素预算下只持有一个图像；缩放返回原尺寸像素一致；不同 span/透明度以及动画独立；fill/stroke 分离；跨视图与文档替换隔离；失败文字元素不残留径向资源 owner。另七项收敛测试检查语料原始字节与许可、缓存开关/重复缩放像素一致性、实际截图、240 次编辑/重挂接/缩放、恶意 XML/深度/数量预算、循环 feImage 和超细卷积网格的拒绝与后续正常文档恢复。

新增可运行演示后，干净全量测试通过 **806/806，失败/错误/跳过均为 0**。实际演示包含 38 个可选样例（本轮新增 11 个），已通过 Monocle 无显示器后端执行显示窗口路径（--smoke-show），逐样例检查、编辑交互与中文界面截图见演示交付记录。最终原始基线补丁复验由最终交付记录补充，此处测试不是最终补丁复验的替代品。

## 同版本重复性与持续编辑

最终同一个 JAR、同一路径/参数，在四对 AB/BA 顺序的八个新 JVM 中执行。标签仅存在于外部记录文件名，未传入 Java 程序。每个工作负载固定 30 轮预热、30 个样本，四工作负载共保留 **960 个样本**，未删除离群值。JAR 与完整测试类/资源树在各进程前核对身份。

**预先声明的 5% 配对中位数筛查未通过：16 对工作负载比较中 14 对超限。** 因此没有建立可用于前后优化因果比较的稳定基线，不进行速度提升或代码回退宣称。资源复用的收益仅以图像身份、预算与正确性测试说明。

| 工作负载 | 四对中位数相对差 | 各进程中位数范围（微秒/操作） | 超过本进程中位数两倍的样本 | 观测到 GC 的样本 |
|---|---|---:|---:|---:|
| parse_corpus | 2.18% / 32.27% / 5.91% / 57.47% | 59.10–113.08 | 18 | 8 |
| create_snapshot | 6.71% / 9.92% / 14.84% / 6.20% | 2176.27–3074.55 | 17 | 0 |
| repeat_snapshot | 6.07% / 15.37% / 24.83% / 3.79% | 79.10–101.52 | 29 | 0 |
| resize_snapshot | 24.09% / 120.65% / 46.74% / 10.77% | 181.34–1111.62 | 15 | 0 |

解析的八个进程均有明显的进程内下降趋势：后半段中位数/前半段为 0.49–0.79。有限预热与运行时编译/缓存状态是值得单独设计实验的假设，而不是已证明的原因。其他工作负载也有长尾与漂移；其中没有观测到 GC，因此不能用 GC 单独解释全部波动。前后主机负载记录约 2.19→1.96，但进程可见性有限，负载数值本身不证明竞争来源。没有发现可移除的并发构建或其他明确竞争证据，不反复重跑寻求通过，不更改门槛，不丢弃失败配对。

连续编辑实际完成 **300 秒、6000 次替换/重挂接/缩放/动画 seek/快照**，使用固定 256 MiB 最大堆。最大场景节点 18，严格诊断为空，旧文档及脱离场景的缓存标志均清理，最低编辑吞吐断言通过。观测堆使用量 11.46–61.30 MiB，末次 36.18 MiB，GC 次数增量 53。未强制 GC；600 个批次观测全部保留。这只说明这次有界运行未观察到失败，不证明不存在内存泄漏或可无限运行。

### 单次预登记长预热诊断

针对主实验的解析进程内下降趋势，额外登记一个固定协议：独立测试入口、预热 300 批、测量 60 批、四对 AB/BA、相同工作负载批大小和 5% 筛查。原实验入口/类文件及全部失败原始数据不变，主 JAR 字节不变；所有诊断进程使用相同参数。只检查稳定性/漂移分布，不以较快的数值宣称代码优化。预登记时间、原入口类 SHA256 和停止规则记录在 `warmup-diagnostic-preregistered.json`。诊断结束无论通过与否均停止，不继续挑选通过结果。结果：保留 **1920 个诊断样本，16 对比较仍有 12 对超过 5%**。解析的后半/前半中位数比变为 0.877–1.199，不再出现主实验每个进程均持续下降的相同模式；但解析相对 MAD 仍约 25.5%–34.8%，说明延长预热并未建立稳定基线。其他负载仍有明显漂移/长尾。这个差异只支持继续将稳定化视为测量问题，不能隔离或证明 JIT、缓存、调度或 GC 的因果贡献。

按照预登记规则在这一诊断后停止。两组失败筛查和全部原始样本均保留；不再增加实验，不做前后速度比较。限制结论是：此环境和这两种固定协议未形成足以支持优化因果比较的稳定基线。
